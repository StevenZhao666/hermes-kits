# 记忆整理流程

> `<HERMES_HOME>`：Windows 是 `%LOCALAPPDATA%\hermes`，macOS / Linux 是 `~/.hermes`。

## 触发条件（满足任一）

- 机主说「整理记忆 / 清理 memory / 记忆乱了」
- 系统提示里显示两个记忆文件到上限的 **80%**（如 `MEMORY [83% — 1,140/1,375 chars]`）
- 刚往 memory 里写过东西，写完超阈值
- 每周定时任务里执行（见 memory-auto-cleanup-workflow）

## 检查（用 execute_code 现算，不依赖外部脚本）

读 `<HERMES_HOME>/memories/MEMORY.md` 和 `USER.md`，算四件事：

1. **使用率** = 内容字符数 ÷ 上限（MEMORY 2200 / USER 1375）
   - ⚠️ 按**字符数**算，不是文件字节数。中文一个字 3 字节，用文件大小算会虚高约 3 倍，阈值判断全错。
2. **超 3 行的条目**（项目细节没迁走）
3. **悬空指针**：memory 里提到的 skill 名，是否真在 skills 目录里存在
4. **重复条目**：意思重复的可以合并

## 分类与处理

| 类型 | 判断 | 处理 |
|---|---|---|
| 待迁移 | 超过 3 行 + 属于某个具体项目 | 内容写进对应 skill，memory 缩成一行指针 |
| 留在 memory | ≤3 行，或全局偏好 / 环境事实 | 不动。机主明确说过的话**只能精简，不能删** |
| 需要新建 skill | 属于项目但没有对应 skill | 先建 skill，再迁移 |

## 流程

1. 扫描、分类，判断每条的目标归属
2. 列计划给机主看：

```
计划迁移：
  条目A (5行) → xxx skill，合并到"某节"
留在 memory：
  条目B (1行) → 全局偏好，不动
```

3. 确认后执行：**先建/改 skill，再改 memory**（顺序反了会在中途丢信息）
4. 报告：整理前 → 整理后字符数 + 改了哪些条目、为什么

## trim 规则（迁移后 memory 留什么）

```
迁移前: "某项目VM信息：3台VM 104/123/174，SSH 走 proxy.host:2174/2175"
迁移后: "某项目→加载 xxx skill。3台VM: 104/123/174。"
```

保留：项目名 → skill 名 + 一句最关键的标识（人名、编号、数量）。

## 原则

1. 主动发现、主动动手，但建议留变更说明（改了哪、改了啥、为什么）——不然机主下次看到记忆变了会困惑。
2. 迁移前先读目标 skill，别写重复内容。
3. 不删机主的工作规则和偏好——可以压缩措辞，不能删内容。
4. 重复内容去重时保留更完整的那版；不确定就保持原样。
5. 触发词建议只指向确实存在的 skill；目标不存在就先建、再写触发词。

## 备份

动手前建议先把两个文件各存一份副本：`MEMORY.md.bak-<日期>`（同目录）。改坏了能一键盖回去。

## 验证清单

- [ ] 整理后每条 ≤3 行
- [ ] 触发词对应的 skill 都能加载
- [ ] 迁移的内容在目标 skill 里能找到
- [ ] 信息量没有减少
